# design-qa — 디자인 비평/QA (판단형, 브라우저 X)

성복교회 웹(Next.js 15 + TS + Tailwind 4)의 *완성된* UI를 **DESIGN.md 바**에 비춰
점검하는 리뷰 방법론. **리뷰만 한다 — 코드를 수정하지 않는다.** 발견을 리포트로
돌려주고, 수정은 사용자/구현자가 판단한다. 이 파일은 **얇은 절차 + 가드레일**이다 —
바의 내용은 DESIGN.md를, 품질 기준은 메모리를 *가리킨다*. 여기서 복제하지 않는다.

## 0. 정본 먼저 로드 (매번, 복사 금지)

1. **바 정본**: 레포 루트 [DESIGN.md](../../../DESIGN.md) 를 Read. 6차원(토큰 규율·
   카피 톤·모션 바·한글 타이포·a11y·subtraction)과 채점 표기가 거기 있다.
2. **품질 기준 메모리** 회상: `feedback-hero-design-bar`(모션·적합성),
   `feedback-copy-tone`(문구), `feedback-avoid-templating`(시안 다양성). 가드레일이지
   재조합할 틀이 아니다.
3. 문서·메모리가 코드 현실과 어긋나면 **현재 코드를 정본**으로 보고 어긋남을 보고.

## 1. 대상 파악

1. 인자로 파일·디렉토리·범위가 주어졌으면 그쪽 우선.
2. 아니면 작업트리 변경분의 **UI 파일**(PascalCase `.tsx` 컴포넌트 · `src/app/**`
   라우트 · `.css`): `git diff` / `git diff --staged` / `git status --short`.
3. **프리뷰 코드(`*-preview/`·`_variants/`)는 차단 대상 아님** — 던져버릴 시안.
   정식 위젯으로 승격된 코드만 본다.
4. 변경된 컴포넌트는 diff 라인만 보지 말고 **파일 전체와 사용처까지 Read**.

변경된 UI가 없으면 그 사실을 보고하고 종료한다.

## 2. 체크 항목 (DESIGN.md 6차원)

- **토큰 규율** — 먼저 `pnpm design:lint` 를 돌려 결정적 위반(색 하드코딩)을 받는다.
  그다음 토큰 오용(예: `sunday`를 일반 빨강으로)·비-b1 Tailwind 기본색을 눈으로.
- **카피 톤** — 콘텐츠/문구가 영업·환대성인가, 사실 진술의 정중함인가.
- **모션 바** — transform/opacity만인가, 다크/테크·잔카는 없는가, 등장/체류/이탈이
  설계됐는가, **`prefers-reduced-motion` 가드가 있는가**(스크롤·Ken Burns·자동재생·
  무한 keyframe).
- **한글 타이포** — keep-all 깨는 인라인, 헤딩 balance/clamp 누락.
- **a11y** — 밝은 b1 위 대비(특히 `text-b1-muted` 본문 사용), focus 가시성
  (`outline-none` 단독), 의미 이미지 `alt`.
- **subtraction** — 픽셀값 못 하는 장식·중복·요청 안 된 화려함.

## 3. 깊이 규율 + 한계

- 호출 체인 끝까지 추적 후 결론. 위험·핵심 변경은 깨지는 시나리오를 그려본 뒤 판정.
- 옵션 매트릭스로 결정을 떠넘기지 않는다. "이게 문제고 이유는 X, 이렇게 고쳐라".
- **소스만 읽는 한계를 정직하게**: 모션 매끄러움·실제 대비·reduced-motion 동작은
  *의심 제기*까지만 가능하다. 런타임 확정은 마일스톤 라이브 감사(`/design-review`)
  몫임을 명시하고, 해당 항목은 "확인 필요(라이브)"로 표시한다.
- reduced-motion 위반이 `use*` 훅(예: useScrollProgress)에 있으면, 그 파일은 로직으로
  분류돼 code-review로 가니 design-qa 리포트에 "라이브 감사 필요"로 남긴다.

## 4. 출력 형식

심각도별로 그룹화해 보고한다. 각 항목은 `파일:라인` + 문제 + 고칠 방향.

```
## 디자인 QA 결과

### 🔴 must-fix (바 위반)
- `src/.../Foo/index.tsx:42` — <문제> / 고칠 방향: <…>

### 🟡 should-fix (톤·대비·절제)
- `src/.../Bar/index.tsx:13` — <문제> / 고칠 방향: <…>

### 🔵 nit / 확인 필요(라이브)
- ...

### 종합
<한 줄 판정: 승격/머지 가능 · 수정 후 가능 · 막아야 함 + 핵심 이유>
```

지적이 없으면 그렇게 보고하고 무엇을 확인했는지 한 줄로 남긴다. 없는 문제를
지어내지 않는다.
