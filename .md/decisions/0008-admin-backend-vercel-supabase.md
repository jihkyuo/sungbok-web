# ADR 0008: 관리자·백엔드를 Vercel + Supabase 두 서비스로 (파일도 Supabase Storage)

**상태**: 채택
**날짜**: 2026-11-05

## 배경

새 사이트의 콘텐츠(예배 시간·부서·교역자·소식)는 지금 전부 코드 속 TS 파일이라, 문구 하나를 바꿔도 개발자가 코드를 고치고 다시 배포해야 한다. 2027-01 오픈(회의록 D14) 뒤에는 교회 쪽 사람이 직접 고칠 수 있어야 한다.

기존 사이트(sungbok.or.kr, 그누보드 — 메뉴 1개 = 게시판 1개)를 2026-11-05에 실측한 결과:

- 매주 사람이 올리는 것: **주보**(이미지 4장, 88건), **주일광고**(텍스트, 86건), 설교 시트지(PDF).
- 가장 손이 많이 가는 것: **설교 영상 수동 등록**(수요·새벽만 257건, 거의 매일). 유튜브 연동(D3)으로 없앤다.
- 온라인 새가족등록은 네이버 폼을 iframe으로 끼워 넣은 것.
- 트래픽: 글 하나당 조회수는 주보 약 90~110, 광고와 설교 10~27(로봇으로 보이는 균일한 수치는 제외). 추정 월 수천~1만 페이지뷰로, 비용을 정하는 것은 트래픽이 아니라 사진 용량이다.
- 옮겨야 할 파일: 주보 88×4장, 사진첩, 시트지 PDF 55개. 줄여서 저장하면 **150~200MB**. 설교는 유튜브 임베드라 옮길 파일이 없다.

또 하나의 조건: 이 사이트는 **나중에 교회 쪽(다른 봉사자나 업체)에 넘길 수 있어야 한다.**

## 결정

**Vercel(사이트, `/admin` 관리자 화면, 서버 로직) + Supabase(Postgres, 관리자 로그인, 행 수준 권한, Storage 파일 저장) 두 서비스로 간다. 계정은 둘 다 교회 명의로 만들고, Cloudflare나 별도 서버는 두지 않는다.**

- 백엔드는 `sungbok-web` 안에서 TypeScript로 작성한다(Route Handler, Server Action). 넘길 저장소는 1개다.
- 파일은 Supabase Storage에 둔다. 업로드할 때 줄여서 저장하고(긴 변 2000px 안팎, 장당 300KB 안팎), 방문자에게는 `next/image`로 최적화해서 보여 준다. 파일 주소는 DB에 저장해서, 나중에 저장소를 바꿀 수 있게 한다.
- 도메인은 지금 있는 곳(업체나 등록 대행사)에서 레코드만 Vercel로 돌린다. 네임서버는 옮기지 않는다.
- 무료로 시작한다. 1GB가 차면 그때 Supabase Pro($25/월)로 올릴지, 파일만 다른 곳으로 옮길지 정한다.

## 대안 비교

| 안 | 내용 | 결과 |
|---|---|---|
| A. 개인 OCI VM + `~/dev/apps` 모노레포(Spring, app-core) | 추가 비용이 거의 없고 로그인·업로드·격리를 재사용할 수 있음 | **탈락** — VM과 저장소가 개인 소유이고 단비 운영 장치(podman, blue/green, 배포 창)와 얽혀 있어 교회에 넘길 수 없다. 단비 장애가 교회 사이트로 번진다 |
| C. AWS(Lightsail, EC2) + Spring, 교회 계정 | 익숙한 Spring. 월 $10~12(2GB)부터 | **탈락** — JVM과 Postgres를 한 대에 올리면 2GB는 빠듯하고, 4GB(~$24)면 Supabase Pro와 값이 같다. OS 패치, 백업, SSL, 장애 대응이 넘겨받는 사람의 부담이 된다. 저장소도 2개가 된다 |
| B′. Vercel + Supabase(DB) + Cloudflare R2(파일) | 무료 10GB, 다운로드 요금 없음 | **탈락** — R2에 자기 도메인을 붙이려면 네임서버를 Cloudflare로 옮겨야 한다. 서비스가 3개가 되고, 업로드 권한을 서버에서 따로 확인해야 한다. 지금 용량(약 2년치가 1GB 안)으로는 이득이 작다 |
| **B. Vercel + Supabase(Storage 포함)** | 서비스 2개, 서버 없음, 권한 규칙을 한곳에서 관리(DB와 Storage 모두 RLS) | **채택** |

**관리자 코드 위치** (2026-11-05 재검토 — 사용자 확정):

| 안 | 결과 |
|---|---|
| 별도 저장소(관리자 전용) | **탈락** — 디자인 시스템과 데이터 타입이 두 저장소로 갈라져 일관성(디자인 시스템의 목적)과 정면 충돌. 넘길 저장소도 2개 |
| 모노레포(`apps/web`·`apps/admin`·`packages/ui`·`packages/db`, 앱별 독립 배포) | **탈락** — 독립 배포·앱별 의존성·앱별 Next 버전은 얻지만, workspace 설정·갱신 신호(웹훅+비밀키)·구조 복잡도로 실수 여지가 커진다 |
| **같은 앱 `/admin`** | **채택** — "하나로 관리하는 게 덜 실수한다". 비용(의존성 한 `package.json`, Next 동반 업그레이드, 한쪽만 바꿔도 함께 배포)을 받아들인다. Vercel 배포는 원자적 교체(무중단)·즉시 롤백이라 함께 배포돼도 서비스 중단은 없다 |

Spring 대신 TypeScript를 쓰는 비용(로그인과 업로드를 app-core에서 재사용하지 못함)은 Supabase 기본 기능(Auth, RLS, Storage)이 대부분 대신한다. Supabase는 표준 Postgres라서 나중에 Spring 서버가 필요해져도 같은 DB에 붙이거나 데이터를 그대로 옮길 수 있다. 되돌릴 수 없는 결정은 아니다.

## 결과 / 영향

### 관리 범위 (2026-11-05 사용자 확정)

- **A — 자주 바뀜**: 주보, 주일광고, 행사 포스터 섹션(기간이 지나면 기본 화면으로), 교회앨범, 설교 시트지, 홈 영상·라이브 수동 덮어쓰기(평소엔 유튜브 자동), 부서 정보(사역자, 소개, 사진, 유튜브·SNS 링크)
- **B — 드물게 바뀜**: 예배 시간표, 섬기는 이들 명단, 연혁과 인사말, 성복의 뜰·칼럼
- **C — 새로 추가**: 새가족 등록 폼과 담당자 알림(네이버 폼에서 이관), 교회 일정 캘린더, 온라인 헌금 안내(계좌 표시만, 결제 없음), 차량 운행과 주차 안내, 기도 요청 접수(비공개), 선교 소식, 사이트 전체 긴급 공지 띠
- **하지 않음(지금은)**: 교인 로그인과 교인 전용 화면, 자유게시판, 예약과 결제

### 권한

- **사무 담당**: 전부. 부서 담당자가 할 수 있는 일을 모두 포함하고, 계정 발급과 부서 지정도 맡는다.
- **부서 담당자**(8개 부서): 자기 부서의 페이지와 사진만.
- 공개 방식: 부서 담당자가 올린 글은 **바로 공개**하고, 사무 담당이 언제든 내리거나 고칠 수 있다. *(구현 쪽 판단 — 확인 단계를 두면 올리는 사람이 줄어든다. 바꿀 수 있음)*

### 후속 작업과 리스크

- **같은 앱이라 생기는 위험과 막는 장치**(패키지 2에서 구현):
  - 공개 사이트 코드가 관리자 전용 라이브러리를 import하면 방문자 번들이 무거워진다 → 공개 쪽 경로(`src/domains/*`, 공개 라우트)에서 관리자 전용 모듈과 라이브러리를 import하지 못하게 lint 규칙(`no-restricted-imports`)을 건다.
  - 관리자 쪽 빌드 오류가 홈페이지 배포를 막는다 → 배포 전 `pnpm build`를 필수로 한다.
  - Next 업그레이드는 양쪽을 함께 확인한다.
- **DB 구조 변경은 배포와 원자적이지 않다**: 컬럼 삭제나 이름 변경은 "추가 → 코드 배포 → 제거" 순서로 나눈다(무중단 배포를 유지하는 조건).

- **기존 자료 이전**: 공개 게시판을 한 번만 긁어 오는 스크립트로 옮긴다(글, 이미지, PDF, 작성일). 기존 사이트가 닫히기 전에(회의록 O7) 마쳐야 한다.
- **Vercel 요금제**: Hobby는 "비상업·개인 용도"이다. 결제와 모금이 없는 교회 사이트면 괜찮다는 의견이 많지만 공식 정책은 아니다. 관리자가 여러 명이거나 정책이 애매하면 Pro($20/월). 오픈 전에 확인한다.
- **Supabase 무료 구간**: DB 500MB, Storage 1GB, 월 5GB 다운로드 트래픽, **7일 동안 활동이 없으면 잠든다**. 방문 트래픽으로 대부분 깨어 있겠지만, 잠들지 않게 하는 장치가 필요한지 구현할 때 확인한다.
- Vercel Hobby의 이미지 최적화 한도를 구현할 때 확인한다.
- 정확한 방문자 수는 그누보드 관리자 화면의 "회원관리 → 접속자집계"에서 받는다(교회 측 관리자 계정 필요).
- 남아 있는 `Dockerfile`, `docker-compose.yml`, `output: 'standalone'`은 Vercel 배포에는 필요 없다. 정리 여부는 따로 정한다.
- 관리자 화면은 `sungbok-web` 안에 두므로 **기존 디자인 토큰과 shadcn 컴포넌트를 함께 쓴다**. 디자인 시스템 범위는 다음 결정에서 다룬다.
